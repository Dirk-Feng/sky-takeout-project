# MySQL 与 Redis 的事务及缓存一致性

## 1. 为什么不能直接使用一个事务？

MySQL 和 Redis 是两个独立的数据资源，各自具有自己的执行和事务管理机制。

Spring 的普通 `@Transactional` 主要管理 MySQL 等关系型数据库事务，不会自动协调 Redis 操作。

Redis 单条命令通常具有原子性，但原子性不代表可以回滚。

例如：
- MySQL UPDATE 成功，但尚未提交。
- Redis DEL 已经执行。
- Java 后续发生异常。
- MySQL 回滚，但 Redis 删除操作不会自动恢复。

因此，不能认为将两个操作写在同一个 Java 方法中，就能保证它们一起成功或失败。

## 2. 常见的缓存更新策略

采用 Cache Aside（旁路缓存）模式：

1. 管理端修改 MySQL。
2. MySQL 事务提交成功。
3. 删除对应 Redis 缓存。
4. 用户下次访问时，缓存未命中。
5. 查询 MySQL 最新数据。
6. 重新写入 Redis。

注意：缓存删除应该在数据库事务提交成功后执行，例如使用 Spring 的 afterCommit 回调。

## 3. 缓存一致性的兜底措施

- TTL：避免缓存长期保留。
- 失败重试：Redis 删除失败后进行补偿。
- 业务校验：订单金额等关键业务数据以数据库为准，不能直接相信缓存或前端传入的价格。

TTL 不能保证实时一致性，只是降低旧缓存长期存在的风险。

## 4. 事务与锁的区别

事务：解决一组操作的提交与回滚问题。

锁：控制多个线程对共享资源的并发访问。

锁不能代替事务，也不能自动保证 MySQL 和 Redis 跨系统原子提交。

如果采用分布式锁，需要保证所有相关访问方遵守同一套锁协议，并考虑锁过期、异常释放等问题。

## 5. 当前苍穹外卖采用的方案

MySQL 事务 + 提交后删除 Redis 缓存 + TTL。

当前菜品展示缓存不引入复杂的分布式事务和分布式锁。

订单提交时重新校验数据库中的真实价格，保证关键业务不依赖可能过期的缓存数据。
