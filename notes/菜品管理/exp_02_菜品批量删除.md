# TASK07-DISH-03 — 菜品批量删除

## 一、接口设计

接口：

`DELETE /admin/dish?ids=1,2,3`

Controller 使用：

```java
@RequestParam List<Long> ids
```

接收多个菜品 ID，由 Service 统一处理批量删除业务。

## 二、业务流程

本次涉及三张表：

- `dish`：菜品主表。
- `dish_flavor`：菜品风味表，通过 `dish_id` 关联菜品。
- `setmeal_dish`：套餐与菜品的关联表。

完整业务流程：

```text
接收 ids
   ↓
查询菜品，检查是否全部存在
   ↓
检查是否存在起售中的菜品
   ↓
检查是否存在套餐关联
   ↓
删除 dish_flavor
   ↓
删除 dish
   ↓
事务提交
```

### 业务限制

1. 菜品必须存在。
2. 起售中的菜品不能删除。
3. 已经关联套餐的菜品不能删除。
4. 所有菜品均满足条件，才能执行批量删除。

如果存在不符合条件的菜品，拒绝整个批量删除操作。

## 三、关键设计思想

### 1. 批量操作：整体成功或整体失败

批量操作可以有两种设计：

- 部分成功：符合条件的删除，不符合条件的跳过。
- 整体失败：只要有一个不符合条件，整个操作都拒绝。

本次选择整体失败。

原因：用户的操作意图是删除一批菜品，而不是删除其中能够删除的部分。整体失败可以让用户重新检查全部选择，避免产生意料之外的部分删除结果。

注意区分：

- 整体成功或失败：业务层面的设计决策。
- 事务：保证数据库操作原子性的技术手段。

两者相互配合，但不是同一个概念。

### 2. 删除前的业务校验

删除不是简单执行 DELETE，而是需要先判断是否满足业务约束。

例如：

- 起售中的菜品不能删除。
- 被套餐引用的菜品不能删除。
- 仍有菜品关联的分类不能删除。

这体现了后端开发中的业务规则管理：不仅要知道如何执行操作，还要明确什么情况下允许执行。

### 3. 多表删除顺序

由于 `dish_flavor.dish_id` 关联 `dish.id`，因此先删除风味，再删除菜品。

`setmeal_dish` 是套餐关联表，如果发现菜品已经被套餐使用，则直接拒绝删除，不主动删除套餐关联。

### 4. 批量 SQL

使用 MyBatis XML 的 `<foreach>` 构造 `IN` 条件：

```xml
<foreach collection="ids"
         item="id"
         open="("
         separator=","
         close=")">
    #{id}
</foreach>
```

例如生成：

```sql
DELETE FROM dish
WHERE id IN (1, 2, 3);
```

批量查询和批量删除可以减少数据库交互，避免针对每个 ID 单独执行 SQL。

使用 `#{}` 进行参数绑定，避免直接拼接用户输入。

## 四、事务管理

在 Service 的完整批量删除方法上使用：

```java
@Transactional
```

将业务校验通过后的多表删除操作放在同一个事务中。

例如：

```text
删除 dish_flavor 成功
       ↓
删除 dish 失败
       ↓
事务回滚
       ↓
恢复到操作之前的数据库状态
```

保证多表删除的原子性。

注意：事务保证本次写操作的原子性，但不自动解决并发检查问题。高并发场景还需要进一步考虑锁和数据库约束。

## 五、本次学习收获

1. 批量操作需要先明确业务语义，决定采用部分成功还是整体失败。
2. 删除操作首先需要进行业务约束检查，而不是直接执行 DELETE。
3. 多表操作需要考虑数据之间的依赖关系和删除顺序。
4. MyBatis foreach 可以实现批量查询和批量删除。
5. Service 是组织完整业务流程和事务边界的合适位置。
6. 业务规则、事务管理和并发控制是不同层次的问题。
