# TASK07 — 用户端购物车模块

## 一、模块概述

本模块实现苍穹外卖用户端购物车管理，使用 MySQL 保存购物车数据，不使用 Redis。

主要功能：

1. 加入购物车
2. 查看购物车
3. 清空购物车
4. 减少购物车中某个商品的数量（扩展功能）

采用 Spring Boot 三层架构：

- Controller：接收用户请求。
- Service：处理购物车业务逻辑。
- Mapper：执行 MySQL 数据操作。
- Entity：ShoppingCart，表示购物车记录。

## 二、为什么使用 MySQL 而不是 Redis？

购物车数据具有一定的持久化需求，用户可能在不同时间访问购物车。

使用 MySQL 的优势：

- 数据持久化，避免购物车数据因缓存过期而丢失。
- 方便与订单业务衔接。
- 可以直接使用 SQL 完成数量更新、条件查询和批量删除。
- 事务管理相对简单。

对于当前项目，MySQL 已经能够满足需求，没有必要额外引入 Redis。

## 三、购物车商品的识别

ShoppingCartDTO 主要包含：

- dishId：菜品 ID
- setmealId：套餐 ID
- dishFlavor：菜品口味

其中：

- dishId 和 setmealId 是互斥关系，一次只能添加菜品或套餐。
- dishFlavor 是菜品的附加属性，套餐不使用该字段。

判断是否为同一个购物车商品时，需要综合考虑：

- 当前用户 userId
- dishId 或 setmealId
- dishFlavor（菜品场景）

例如：

用户添加：
- 宫保鸡丁（微辣）× 1
- 宫保鸡丁（微辣）× 1
- 宫保鸡丁（特辣）× 1

最终购物车应该是：

- 宫保鸡丁（微辣）× 2
- 宫保鸡丁（特辣）× 1

不能只根据 dishId 判断，否则不同口味可能被错误合并。

用户身份从 JWT 认证后的 BaseContext 获取，不能相信前端传入的 userId。

## 四、四个接口的业务逻辑

| 接口 | Method | Path | 功能 |
|---|---|---|---|
| 加入购物车 | POST | /user/shoppingCart/add | 添加菜品或套餐 |
| 查看购物车 | GET | /user/shoppingCart/list | 查询当前用户购物车 |
| 清空购物车 | DELETE | /user/shoppingCart/clean | 删除当前用户全部购物车记录 |
| 减少商品数量 | POST | /user/shoppingCart/sub | 数量减一，必要时删除记录 |

### 1. 加入购物车

判断当前用户是否已经添加过相同商品：

- 已存在：数量加一。
- 不存在：从数据库查询商品信息，创建购物车记录，初始数量为 1。

商品名称、图片和价格等信息由服务端查询数据库取得，不信任前端提交的商品价格。

已有记录的数量增加可以使用数据库原子更新：

```sql
UPDATE shopping_cart
SET number = number + 1
WHERE ...;
```

避免先查询数量，再由 Java 计算并覆盖更新。

首次插入仍然存在并发重复插入的可能，需要结合数据库约束考虑。

### 2. 查看购物车

根据当前登录用户的 userId 查询购物车。

只返回当前用户的数据，不允许不同用户之间共享购物车记录。

### 3. 清空购物车

根据当前登录用户的 userId 执行批量删除。

不能执行无条件的全表 DELETE。

### 4. 减少一份商品（扩展功能）

业务规则：

- number > 1：数量减一。
- number = 1：删除对应购物车记录。
- 商品不存在：不能误修改或删除其他记录。

采用条件 SQL 优化，避免先 SELECT 再判断。

第一步：尝试原子递减。

```sql
UPDATE shopping_cart
SET number = number - 1
WHERE id = #{id}
  AND user_id = #{userId}
  AND number > 1;
```

通过 SQL 返回的受影响行数判断是否更新成功。

如果更新成功，直接结束。

如果更新 0 行，再执行：

```sql
DELETE FROM shopping_cart
WHERE id = #{id}
  AND user_id = #{userId}
  AND number = 1;
```

两条 SQL 都需要完整限定商品身份，避免误操作其他用户或其他口味的商品。

## 五、值得记录的后端工程知识

### 1. 数据库原子更新

对于计数器的增减，优先考虑让数据库直接完成计算。

不推荐：

```text
SELECT 当前数量
    ↓
Java 读取 number
    ↓
number - 1
    ↓
UPDATE 覆盖原值
```

推荐：

```sql
UPDATE shopping_cart
SET number = number - 1
WHERE id = #{id}
  AND number > 1;
```

优点：

- 减少数据库往返次数。
- 避免 Java 读取旧值后覆盖更新造成的丢失更新。
- 利用数据库原子更新能力处理并发。

### 2. 事务的使用

事务不是由操作几张表决定的，而是由一组业务操作是否需要保证整体性决定的。

例如：

- 单条 UPDATE：通常不需要额外声明事务。
- 先 UPDATE，再 DELETE：需要考虑事务。
- 创建订单，再创建订单明细：需要事务。
- 修改 MySQL，再删除 Redis：普通数据库事务不能保证两边一起回滚。

购物车减少数量时，可能涉及 UPDATE 和 DELETE 两条 SQL，因此可以在 Service 方法上使用 `@Transactional`，保证这组数据库操作的整体性。

### 3. 三层架构的职责划分

| 层次 | 主要职责 |
|---|---|
| Controller | 接收请求、参数传递、返回 Result |
| Service | 业务流程编排、业务规则、事务管理 |
| Mapper / MySQL | 条件查询、原子更新、删除 |

一个重要的开发经验：

**能通过 SQL 条件、原子更新和受影响行数解决的问题，就不要先查询数据库，再拿到 Java 中反复判断。**

但不要把所有业务逻辑都塞进 SQL，Service 仍然负责业务流程和规则。

## 六、后续需要注意的边界

1. 首次添加商品存在并发重复插入风险，后续可以考虑数据库唯一约束。
2. 购物车中的商品价格可能是加入时的快照，提交订单时必须重新校验商品状态和实际价格。
3. 不同用户的购物车必须严格隔离。
4. 菜品口味必须参与购物车商品身份判断。

## 核心知识点总结

1. 购物车使用 MySQL 保存，不必为了使用 Redis 而引入缓存。
2. 菜品和套餐互斥，菜品口味参与商品身份判断。
3. 使用 SQL 原子递增、递减，减少数据库往返和并发更新问题。
4. 使用受影响行数判断 SQL 执行结果。
5. 事务用于保证一组数据库操作的整体性，而不是简单由涉及的表数量决定。
6. Service 负责业务编排，数据库负责高效的数据操作。
